# Fork Compliance Checklist

Legal obligations for distributing this fork commercially, per the Apache
License 2.0 (`LICENSE`) and the upstream project's statements in `README.md`,
`NOTICE`, and `CONTRIBUTING.md`. Run the per-sync checks after every upstream
merge (see `fork/RUNBOOK.md`).

## Standing obligations (Apache-2.0 §4)

1. **License retention** — a copy of Apache-2.0 ships with every distribution.
   electron-builder does **not** package it automatically: `LICENSE` and `NOTICE`
   are explicit `extraResources` entries in `apps/shell/electron-builder.cjs`, so
   both land in the installer's `Resources/` beside `THIRD-PARTY-NOTICES.txt`.
   Verify all three in the built installer before each release.
2. **NOTICE retention** — upstream `NOTICE` ("GenOffice / Copyright 2026
   Mainfunc, Inc.") must be carried through. Do not delete or rewrite the
   copyright line; our fork's own notice may be added alongside it.
3. **Modified-files notice** — files modified relative to upstream must be
   marked (Apache-2.0 §4(b)). Keep the running list below.
4. **Third-party notices** — run `node tools/gen-third-party-notices.mjs`
   before packaging; electron-builder includes the output in the bundle.

## Hard restrictions

- **Trademark**: "GenOffice" and "Genspark" names/logos are trademarks of
  Mainfunc, Inc. and are NOT licensed to us (README License section, Apache-2.0
  §6). Our product must ship under our own brand. Every user-visible occurrence
  must be swept (see per-sync check #3).
- **`ee/` directory**: under the proprietary GenOffice Enterprise License, not
  Apache-2.0. It is currently empty (LICENSE/README only) but must never be
  packaged or distributed, and never contributed to.
- **Genspark services**: Genspark sign-in and `gsk` search endpoints run on
  Mainfunc's servers. Our build must default to BYOK providers and the keyless
  search fallback, and must not ship Genspark credentials.

## Per-sync checks

1. `ee/` exclusion: confirm nothing under `ee/` is referenced by
   `apps/shell/electron-builder.cjs` (files/extraResources) or added to
   installers.
2. NOTICE intact: `git diff main -- NOTICE LICENSE` shows no deletions.
3. Trademark sweep: `npm run check:brand` (fatal tier must pass; the advisory
   tier reports remaining vendor-name strings). Then a visual pass over the
   built app's About/settings screens, counting only user-visible strings.
4. Fork chrome intact: `npm run check:app-chrome` — asserts the Home launcher
   markup/styles, fork-only design tokens and fork-only tab kinds survived the
   merge. A pass here does not prove the UI looks right; open Home once.
5. Updater feed: confirm the auto-updater does not point at Genspark's release
   feed (fork must own its update channel or have updates disabled).
6. Modified-files list: update the table below.

### Optional AI extraction — the fork's first outbound network call from Tenders

The owner decided that Tenders may offer **optional AI extraction** alongside its local rule
engine: a model provider the user configures (the suite's existing BYOK plumbing — no
credentials shipped, no new service, nothing of Mainfunc's) may read the tender's text, or a
scanned page's image. Recorded here because it is a **deliberate fork decision, not a merge
artifact**, and because it is the first time this fork's Tenders pane sends anything off the
machine.

- **Off by default and additive.** No API key or no network means the app behaves exactly as it
  did before the feature existed; the local, offline rule engine is what always runs.
- **What leaves the machine:** the page text of the document the **user** opened, or, for a page
  with no text layer, that page's image — to the provider the user configured, only when the user
  turns the feature on.
- **What does not change:** nothing AI produces is ever confirmed. Every value a model returns is
  an unconfirmed suggestion (`suggestedBy: 'ai'`), no AI output may write `confirmed`, and the
  renderer never handles an API key (main injects it per request).
- **Still forbidden:** tender-marketplace scraping and portal/email submission. AI extraction
  reads a document the user already has, only to lift values for that user to confirm — it never
  fetches a tender from a marketplace, never acts as the user, and never submits anything. It is
  also not AI-authored methodology: the pass extracts what the document says.
- Contracts: `docs/tenders-hardening/contracts-and-invariants.md` §5a; the boundary amendment:
  `docs/tenders-hardening/README.md` ("Product-boundary reminder").

### Tenders reaches two external sources by design — both optional, both off unless enabled

Tenders now has exactly **two** outbound reaches, and both are recorded here because they are
**deliberate fork decisions, not merge artifacts**:

1. **The model provider the user configures** (optional AI extraction, above) — the suite's
   existing BYOK plumbing. No credentials ship, no new service is involved, nothing of Mainfunc's,
   and nothing leaves the machine unless the user turns the feature on.
2. **National Treasury's public eTenders open-data feed** (tender discovery,
   `apps/tenders/src/main/discovery-client.ts`). The feed is **keyless**, published under the
   **Public Domain Dedication and Licence (PDDL) 1.0**, and read from the **main process** against
   an https-only, exact-host allow-list validated before every request, with per-hop redirect
   re-validation, byte caps, timeouts and an on-disk cache. The reach is bounded to
   `ocds-api.etenders.gov.za`, `data.etenders.gov.za` and `www.etenders.gov.za`, and no document is
   ever mirrored — a linked tender document is opened on the Treasury site.

Licensing position for source 2: Treasury publishes the feed for reuse under PDDL 1.0 and the app
reads it directly rather than redistributing it; nothing from the feed is bundled, cached beyond
the user's own machine, or re-hosted. `describeCoverage()` in `shared/discovery.ts` surfaces
Treasury's own licence and status statements in the UI, so the user always sees what the data is
and what it is not.

- **Optional, and off unless enabled.** Discovery fetches nothing until the user opens the
  Discover pane; the saved list is read from disk with no network at all; **deadline reminders are
  computed entirely on this machine and reach no network** (`shared/reminders.ts`,
  `main/reminders-scheduler.ts`). DOCX intake is a local file read.
- **Nothing machine-sourced is confirmed.** A discovered opportunity carries
  `provenance: 'discovery-feed'` and imports with every field `unconfirmed`, exactly like an AI
  suggestion. Nothing in these modules can write `confirmed`.
- **Not a marketplace scrape.** Tender-marketplace scraping and portal/email submission remain
  forbidden. Discovery reads one named, licensed, public government feed from main under an
  allow-list — it does not crawl a commercial marketplace, does not act as the user, and does not
  submit anything anywhere.
- **The diagnostics log is local-only and is not a third reach.** `<userData>/tenders/tenders-diagnostics.log`
  (1 MiB × 3 files) is written on this machine, is never uploaded and is not networked; the sink
  refuses document-bearing detail keys and drops objects passed as values, so it carries counts,
  codes and reasons rather than tender text. It adds no outbound reach — the two above remain the
  only ones (see `docs/tenders-hardening/contracts-and-invariants.md` §3e).
- **The feed is a public beta and the app says so.** Treasury states its accuracy is not
  guaranteed and that it must not be used for critical decision making or legal purposes;
  municipalities and state-owned enterprises appear only when they volunteer data. Those limits are
  product facts shown verbatim, not footnotes (see `docs/tenders-hardening/contracts-and-invariants.md`
  §3b).

  - 9 specs were converted off the Unix `zip`/`unzip` CLI to jszip, following the pattern already in `sheets-xlsm` / `sheets-ribbon-batch` / `slides-font-manager`. Root cause worth remembering: **`zip` is genuinely absent on stock Windows while Git Bash supplies `unzip`**, so only the archive-_writing_ specs failed while the `unzip -p` readers silently kept working.
  - `theme-pipeline` / `theme-visual*` now assert the fork's contract (main resolves the preference and renderers stamp the resolved `light|dark`) instead of upstream's null-while-system.
  - `settings-media-search` no longer hardcodes Genspark/TypeSafe as the search provider — the fork's default is Serper.
  - `ai-panel-side-settings` was a spec bug, not a product defect: two `genoffice-app://docs` pages exist (the fork's detached idle prewarm renderer and the real tab), and the prewarm one reports a permanently 0×0 viewport while still exposing `.ProseMirror`, so the spec's page lookup grabbed it.
  - `tenders-intake-review` / `tenders-lifecycle` close the readiness and milestones drawers with Escape (the drawer's own documented gesture) and assert they actually went away.
- **One genuine product defect, found by those specs and deliberately left unpatched** (a UI decision that is settled, and upstream code):
  - **The docs respell after re-enabling spellcheck is unreliable on Windows.** `e2e/docs-spellcheck-reenable.spec.ts` counts red spelling-marker pixels after re-enabling with no user input; measured outcomes across runs are full recovery, ~8.5 s delay, or never. That is native spellchecker scheduling — the app code and the test both already acknowledge Windows samples asynchronously — and the spec is byte-identical to upstream.
- **The Tenders defects those specs surfaced were fixed, not left unpatched.** `apps/tenders` is **fork-only** — `git ls-tree main --name-only apps/` lists only docs/html/markdown/pdf/sheets/shell/slides — so "upstream code" was never a valid reason to leave one, and no upstream fix can ever arrive:
  - **The tenders drawer close control was unreachable by pointer.** The workspace toolbar is `position: sticky; z-index: 30` (`apps/tenders/src/renderer/src/styles/responsive.css:79-83`) while the shared `Drawer` aside is `z-20`, so its title row — title and X — painted _underneath_ the toolbar. Measured with the drawer open before the fix: the X occupied `{x:1306,y:14,w:37,h:29}` and `document.elementFromPoint(1325,29)` returned the toolbar's overflow trigger. Every `Drawer`-based aside was affected (readiness, vault, milestones); `TrashDrawer` uses `z-30` and was immune. Fixed by measuring the toolbar and starting the drawer at its bottom edge (`toolbarBottomOffset` + `style={{ top: toolbarOffset }}` in `components/Drawer.tsx`); `e2e/tenders-a11y-theme.spec.ts` test 6 asserts the close control is hit-testable and `apps/tenders/tests/drawer-toolbar-offset.test.ts` pins the arithmetic.
  - **The Tenders demo assets were never shipped.** electron-vite's renderer root is `src/renderer`, so vite's default `publicDir` was empty and no `demo/` was emitted at all: "Load demo RFP" fetched `./demo/sample-rfp.pdf` (a 404) and the sample workspace's vault documents had no file. Fixed with `publicDir: resolve(__dirname, 'public')` in `apps/tenders/electron.vite.config.ts` and `apps/tenders/vite.renderer.config.ts`; `assertModuleTreesPresent` in `apps/shell/electron-builder.cjs` now fails the packaging step when `renderer/demo/sample-rfp.pdf` or `renderer/demo/vault` is absent.
  - **Every drafted proposal was stamped `DRAFT — READINESS NOT INDEPENDENTLY VERIFIED`.** The preload's `projectProposalDto` dropped `id`, and `id` is the only way main can resolve the canonical tender and build an independently verified readiness report. `id` is now projected.
- **An orphaned docs prewarm renderer.** `TabManager.openDocsTab()` clears `prewarmedDocsView` unconditionally, while a path-based open creates a _fresh_ view, so the warm renderer is left detached and alive (it held a renderer process with a mounted blank document in every measurement, and it is what made the `ai-panel-side-settings` page selection ambiguous). Harmless to the UI, but a leak.
- **Docs batch modes silently misreport — upstream regression, surfaced by the new `packages/cli` tests.** `applyDocOps` (`packages/cli/src/formats/docx.ts:513`) counts an op as rejected when the docs executor reports `isError` or an output matching `No matching blocks`, but the merged docs engine returns `isError: false` with that text for an out-of-range target. Consequence: `--best-effort` reports `ok` with every op applied and `--stop-on-error` never stops. Three `batch-modes` tests and one `docx` guard-rail test are gated behind `GENOFFICE_DOCS_REJECT_SOFT_RESULTS=1` so they re-assert the moment the engine is fixed — they were not weakened or deleted. Not caused by this merge's conflict resolution (`packages/cli` is new), but it is a genuine defect to settle with upstream.
